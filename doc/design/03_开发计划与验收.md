## 1. 实施原则

先证明现有 Laya 工程能承载严格单包，再完成最小可玩闭环，最后补齐多代循环和资源表现。每一阶段都有可展示结果和退出条件，不以“代码已写”代替运行证据。

修改开始前重新检查工作区和工程状态，沿用现有目录，不覆盖用户工作。拟新增文件、函数和业务规则在本次文档中是建议，后续实施按用户确认范围推进。

初始工程没有现成测试或命令行发布入口；当前已接入 TypeScript 检查、85 项自动回归及 LayaAir CLI 3.4.2 微信导出。已验证命令见运行记录，不假设存在 npm 构建入口。

## 3. P0：技术路线可行性门禁

### 3.1 最小样本必须包含

- 当前工程的启动场景和已挂载 Main，启动日志能在实际运行中观测到。
- 真实所需的 Laya 2D、UI、微信适配运行代码。
- 一张代表性小图集、一个可点击按钮、一段文本、一个短音效。
- 720 × 1280 设计画布的竖屏布局，顶部和底部安全区检查。
- 保存一个小状态、退出后读取、切后台暂停的最小验证。

这个样本用来验证系统入口和开销，不扩展完整玩法。是否使用 d3、其他运行库和额外字体都必须记录依据。

### 3.2 需要记录的证据

| 证据 | 内容 |
| --- | --- |
| 工程版本 | 仓库提交、脏状态、工程版本字段、实际 IDE 版本 |
| 发布配置 | 平台、压缩选项、模块选择、实际输出目录 |
| 文件清单 | 引擎、适配、脚本、图片、音频、配置分项字节数 |
| 平台计包 | 微信开发者工具版本、上传/预览统计与限制提示 |
| 运行设备 | 操作系统、机型、微信版本、启动与操作结果 |
| 网络边界 | 核心资源来自包内，未用远程下载补资源 |

### 3.3 通过与停止条件

通过：完整最小运行样本能在微信真机启动，必需功能有效，且实际剩余包体足以容纳重新核算后的内容预算。

停止：必需运行包超过上限，或虽然未超上限但剩余空间无法支持已约定的最小内容。此时报告差距，优先检查实际依赖与发布配置，再讨论内容或技术取舍。

不得未经确认切为分包、远程资源、共享引擎插件或另一套引擎；也不得继续投入完整美术生产后再处理限制。P0 的静态预算表不能代替实际通过记录。

## 4. 第一条可玩链路

首条链路限定如下，先验证核心体验：

1. 打开游戏，看到固定村庄、6 名成人、初始资源和 2 座塔。
2. 在已有家庭中迎接 1 名孩子，粮食扣除并安排照料。
3. 开始守夜，生产和口粮结算一次，保存战前快照。
4. 敌人沿道路进入，塔自动攻击，玩家可以敲警钟。
5. 胜利后孩子成长 1 次；第二次被照料并获胜后成年。
6. 玩家选择该角色专长、安排到塔上，并看见属性变化。
7. 退出再进，阶段、资源、角色和候选结果正确恢复。

该链路不要求已经加入全部村规、敌人和特效。验证出生与守村有联系后，再进入 P3 扩充。

## 6. 验证方法分层

### 6.1 静态与配置检查

- TypeScript 编译与 Laya 实际构建。
- 配置 JSON 解析、ID 唯一、引用存在、上限和概率合法。

## 7. 可玩性验收与调参方法

### 7.1 必须人工玩出的结果

- 不看设计稿的新玩家能描述出食物、人口和防守之间的关系。
- 前 5 分钟内能体验到出生、成长与驻塔，且操作目的清楚。
- 至少连续 3 代仍需要安排接班，退休既可预期又不会每几秒打断。
- 旅人与生育都存在使用场景；若只等免费旅人更优，调整间隔或人物价值后再测。
- 不同塔和专长有可解释的优势，没有明显一套配置无视全部预告。

### 7.2 小规模对照

使用同一地图、固定种子和相同输入条件比较不同策略：早生育与晚生育、少人口高效率与接近满人口、偏箭塔与偏投石、存粮过冬与即时扩建。

记录存活夜数、村门损伤、粮木溢出、无人岗位、出生/成年/退休次数、人工操作频率与玩家理解问题。数值模拟只说明某个策略在模型中的表现，不能直接代表玩家留存或实际感受。

调整顺序建议：先岗位和口粮，再养育与退休周期，再敌人预算和塔属性，最后检查村规。每轮控制改动范围，保留调参前后配置版本和对照结果。
