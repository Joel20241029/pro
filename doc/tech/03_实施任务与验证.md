## 2. 各工作单的最小实现清单

### 2.1 T00：现有 Laya 工程验证

1. 记录仓库提交、脏状态、LayaProject.laya 的版本与本机实际 IDE 版本。
2. 在 IDE 挂载现有 Main 到 Scene，确认只启动一次；不手工猜测场景序列化结构。
3. 加一个真实文本、按钮、小图集、短音效及最小保存读取，以代表将使用的能力。
4. 使用 720 × 1280 设计画布，检查竖屏、居中和安全区。
5. 从实际依赖确认 UI/2D 所需模块，评估移除当前 d3；不手删打包产物中的未知运行库。
6. 用 IDE 的微信发布入口输出真实 game.js、game.json 等文件，保存正式压缩配置与实际输出路径。
7. 在开发者工具和真机验证，并记录平台显示体积、逐文件原始字节和剩余空间。

仓库没有现成构建命令，因此这里不提供虚构的 npm 命令。[Laya 官方通用发布](https://layaair.com/3.3/doc/released/generalSetting/readme.html) 和 [微信发布](https://layaair.com/3.3/doc/released/miniGame/wechat/readme.html) 是操作依据，实际 IDE 与导出结果仍需复查。

### 2.2 T01～T06：可独立验证的业务

业务规则使用普通数据输入与输出，测试夹具不依赖 Laya DOM、节点或微信。用完整开局配置生成第 1 天，再执行明确的命令序列；每步保留输入快照、输出快照、revision、RNG 状态与期望变化。

不要只测试一个私有函数返回“正确的同一个公式”。优先覆盖会造成资源重复、丢人、无法推进、错误回档或帧率差异的可见行为。错误输入必须留下原状态，不以静默修复通过测试。

### 2.3 T07：实际素材接入

只从 [资源清单](../../res/manifest.json) 的白名单选取候选图集和元数据。资源目录内的源母版、GIF、预览、设计概念图和已有大图标不进入运行包。

先做一个角色的完整样本：同一形象的 walk → restFrame → work → restFrame → 驻塔显示；检查身体尺度、脚底和姓名/身份不跳变，再批量接其他角色。对未提供的动作使用资源规范中明确的表现合同，不在代码中“找不到动画就自动取第一组”。

图集使用自定义 frames.json 时，由代码加载 PNG、按矩形建立一次子纹理缓存。若改用 IDE 图集，须关闭逐帧自动裁边，或正确携带 sourceSize/trimOffset/pivot；不能只保留新矩形丢失原点。

## 4. 固定输入测试夹具

### 4.1 规则与随机

| 编号 | 输入或步骤 | 必须观测到的结果 |
| --- | --- | --- |
| R-T01 | 195 粮、产粮 16、口粮 13 | 保存后 198 粮，不能是 187 |
| R-T02 | 已生育扣 20 粮，再开始守夜 | 日结不重复扣生育成本 |
| R-T03 | 第一胎且 lastBirth=null | 满足其他条件即可生育，不要求已守住 4 夜 |
| R-T04 | 亲本天赋相同/不同各一组 | 相同直接继承；不同只在两项中选；推进 RNG 次数符合合同 |
| R-T05 | 孩子已有 1 成长、照料人本夜也将退休 | 胜利后孩子成人 12 夜，照料解除，照料者退休 |
| R-T06 | 同夜两个孩子成年 | 稳定 ID 顺序的两个已存专长选择，均不是 11 夜 |
| R-T07 | 兄妹父母已从历史详情裁剪 | parentIds 仍阻止成家 |
| R-T08 | 初始者和旅人均无父母 | 不因两个空数组误判为同胞 |
| R-T09 | 人口 20 的旅人清晨 | 接纳被拒绝，可谢绝后继续，无悬挂到未来 |
| R-T10 | 无成人、无照料者 | 可以预警后守夜或明确重开，不形成死锁 |
| R-T11 | 年末胜利，选择与上一年不同挑战档 | 新波次只在选档后生成，并记录最终档 |
| R-T12 | LCG seed=1 连续 5 次 | 与文档固定向量一致 |
| R-T13 | 三选一重复生成相同初始状态 | 候选有 3 个不同 ID，顺序与最终随机状态相同 |
| R-T14 | 10,000 次波次生成覆盖解锁日与年末 | 预算精确填满、普通队列≤80、首领≤1、召唤额度≤4 |

### 4.2 战斗回放

回放夹具记录完整战前快照和操作 tick，不用“第几渲染帧点击”表达操作时间。分别以 16.67 ms、33.33 ms、100 ms 和混合长帧驱动；在累计相同逻辑 tick 时，比较门血、存活敌人、出场指针、减速、塔充能与结果。

| 编号 | 场景 | 期望 |
| --- | --- | --- |
| B-T01 | 两名同进度敌人处于射程内 | seq 小者先被选中 |
| B-T02 | 最后敌人同一步到门且随后本可被塔击杀 | 先结算门伤；门血归零则失败 |
| B-T03 | 两座塔同时攻击可死亡主目标 | 后塔重新按当步存活状态选目标，不对已死亡对象重复收益 |
| B-T04 | 更强、相同、较弱减速先后命中 | 强覆盖、同强刷新、弱不延长；足额持续步数 |
| B-T05 | 两个干扰者都在 190 范围内 | 一次 0.80 倍率，不变成 0.64 |
| B-T06 | 警钟同时处于缺粮和干扰 | 正确相乘、持续 100 步、只使用一次 |
| B-T07 | 队列到期但同屏 40 | 保留队列，腾位后出现，无删怪 |
| B-T08 | 首领产生召唤请求后死亡，队列尚未入场 | 已产生请求继续；尚未触发批次取消 |
| B-T09 | 首领到门且普通队列清空 | 召唤队列和批次状态正确关闭后才能胜利 |
| B-T10 | 暂停中换操作员 10 次 | 充能不重置，不凭空获得 10 次攻击 |
| B-T11 | 关闭所有动画与特效 | 战斗结果与开启时一致 |
| B-T12 | 1 倍、2 倍运行同一逻辑输入 | 同逻辑 tick 状态一致，现实耗时不同 |

### 4.3 保存故障矩阵

测试存储适配器应能独立注入读取异常、写前异常、写后抛错、截断字符串和非预期槽变化，不能把“抛异常”一律当作没写入。

| 编号 | 注入点 | 期望 |
| --- | --- | --- |
| S-T01 | 校验候选时失败，尚未尝试写 | 明确拒绝，原进度可继续 |
| S-T02 | 写入成功，读回抛错 | 冻结；核对后确认同一候选，不扣第二次 |
| S-T03 | 写入完全没生效，目标仍是原较旧有效记录 | 两槽基线符合时重写原 serialized，不误判永久冲突 |
| S-T04 | 目标被截断，另一槽未变 | 运行中可核对并重写相同候选；重启按恢复规则处理 |
| S-T05 | 另一槽出现非预期较新有效记录 | 冲突提示，不覆盖 |
| S-T06 | 目标 revision 相同、内容不同 | 冲突提示，不只看序号 |
| S-T07 | 成功落盘后、UI 成功前强制结束进程 | 启动承认已写完整候选 |
| S-T08 | R06 成功后强退，再进 | NIGHT 重打，资源不再结算 |
| S-T09 | R14 成功后强退 | 恢复 DAWN 队列，不再次成长/退休 |
| S-T10 | 最后一项清晨选择已保存，DAY 尚未保存 | 从空 DAWN 队列生成一次波次 |
| S-T11 | FinalizeDawn 写入成功但未读回 | 重试同一波次，不重新抽取 |
| S-T12 | 某槽未知新版、另一槽旧版有效 | 停止自动读取旧版，不宣称恢复成功 |
| S-T13 | 两槽都暂时无法读取 | 错误与重试，不显示无存档 |
| S-T14 | NIGHT 中只保存音效设置 | 战斗基线仍是战前快照，内存继续当前战斗 |
| S-T15 | CRC32 标准测试串和含中文对象 | CRC、UTF-8、键排序结果稳定；损坏可检出 |
| S-T16 | 已失败但 GAME_OVER 尚未写入即强退 | 只能恢复 NIGHT 战前状态，不虚称失败结果已保存 |
| S-T17 | GAME_OVER 写入后、反馈前强退 | 恢复同一失败页；不再战斗、不提前执行传承 |
| S-T18 | 失败保存读回异常后重试 3 次 | 同一失败摘要和 commitId，只确认一次 |
| S-T19 | 第二局失败，且历史详情已经裁剪 | 出生/退休/代数/新发现只显示本局统计，重进数值不变 |

## 5. 序列帧与资源验收

### 5.1 本轮静态交付检查

- 文件确实存在，PNG 可解码，长宽与 manifest 一致。
- 每组动作恰有 4 张不同编号帧，frameIds 都存在，帧号顺序为 00～03。
- 每个动作画布、pivot、透明边界和 atlasTrim 策略一致；图集 rectangle 全部在页内且互不重叠。
- 地表与透明 sprite 分开标记；透明资源不是把棋盘格画进背景。
- 每个动作生成四帧条带与循环 GIF，检查缺失、跨格、截断和明显身份漂移。
- 候选运行图、图集元数据、原始母版和预览分别计量；不给生成母版记“已压进包”。

静态脚本不能证明角色跑起来舒服。正式接入后仍需逐动作观察 1 倍与 2 倍、行走到静止、岗位切换、登塔和前后台恢复。

### 5.2 Laya 与设备上的动画验收

| 编号 | 操作 | 期望 |
| --- | --- | --- |
| A01 | 每个动作持续循环 10 次 | 可感知动作变化；接缝无突变和严重身体漂移 |
| A02 | walk 停止 | 显示配置的 restFrame，不原地踏步 |
| A03 | 同一角色 walk 与已有 work 切换 | 身份、衣服、身体尺度和脚底连续 |
| A04 | 没有专用劳动动画的造型执行该岗位 | 按明确覆盖表使用原造型静止姿态与岗位标记，不换成另一人物 |
| A05 | 暂停、进后台、保存阻塞 | 战斗与角色动画停止；恢复不跳过后台时间 |
| A06 | 2 倍速 | 战斗角色动画随同一时间倍率变化；不独立再次乘速 |
| A07 | 人物左右转向 | 只对允许镜像的造型使用负 scaleX；脚底原点和文字不镜像 |
| A08 | 图集采样到邻近图片边缘 | 没有串色；小图保持可读，不依靠透明外圈当点击区域 |
| A09 | 连续开关人物页、新开村 50 次 | 没有增加第二个动画循环或重复帧纹理缓存 |

## 6. 长期规模与性能

用可控夹具持续推进至少 10,000 夜规则流程。断言人数≤20、塔=4、同屏敌人≤40、普通计划≤80、召唤请求≤4、history≤60、favorites≤20、单份目标载荷≤128 KiB。记录每轮前后 ID 与队列长度，尤其检查退休删除后照料、家庭和塔引用。

长期测试采用明确脚本策略处理清晨事项与岗位；允许测试构造结果用于覆盖结算，但报告必须区分“规则驱动了 10,000 次胜利”与“真实战斗自然存活 10,000 夜”。二者都不证明留存或平衡。

真机最坏场景包含 20 村民、40 敌人、4 塔与 32 个表现上限；持续观察帧时间、Draw Call、节点数、纹理与内存趋势。常规目标 60 FPS，选定低端机约 30 FPS 是待测目标。文件 PNG 很小不代表纹理解码后的显存同样小。

## 7. 包体清单与发布门禁

计包必须以实际导出的微信完整目录与平台统计为依据，分别列出引擎与适配、业务 JS、场景、PNG/图集、音频、配置与其他文件。原始字节、压缩包大小、平台上传统计使用不同列，不混成一个数字。

候选资源的导入模式为 atlas_only：图集 PNG + frames.json + animations.json。runtime 散图是编辑/检查的替代输入，不与同内容图集同时打包。若改由 IDE 打原生图集，记录旧产物移除和新产物白名单，重新计量，不能两套都保留。

发布前确认没有 `res/source/`、`res/preview/`、`res/icon.png`、doc 概念图、生成提示词、`.d.ts`、sourcemap 或未使用模板资源漏入包。当前 144 像素上传图标可以独立提交平台，除非运行界面确实引用，否则不计为游戏内部必需资源。

## 8. 验收记录模板

每次有效验证记录：日期、工作单编号、构建提交与脏状态、配置版本、实际 IDE/微信工具版本、设备和系统、输入快照/种子/操作序列、预期、实测、结论、限制与证据路径。工具脚本、截图、录像、故障日志等放在 `/Users/happyelements/Downloads/` 的本任务子目录。

“通过”只覆盖真实执行的范围：资源文件检查不代表已导入 Laya；Web 不代表微信；静态包体预算不代表上传通过；自动规则测试不代表三代真实试玩。首个可玩版本仍须由真实用户操作出生、照料、成年、选择专长、接班守塔和退出恢复。
