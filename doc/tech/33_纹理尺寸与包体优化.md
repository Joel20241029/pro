# 纹理尺寸与包体优化

后续调整：1.0.15 第二次上传将怪物显示放大 12.5%，按本页同一采样标准提高部分发布尺寸；当前数值见 [35 操作排序与战斗表现调整](35_操作排序与战斗表现调整.md)。下方为最初压缩基线记录。


实施日期：2026-11-13。适用：LayaAir 3.4.2、微信小游戏高清二维正式工程。

## 目标与边界

根据图片在游戏中的最大显示尺寸，减少发布纹理的像素和包体；人物、怪物、建筑的场景尺寸、位置、遮挡、帧数、播放速度和玩法数值保持原样。高清母版、模型、绑定、设计稿、原生预制体与时间轴继续保留，发布包只使用派生图集。

本轮调整 245 张已有派生图片，另增加 5 张独立静态头像。48 组动画的帧顺序、帧数、方向和帧率不变。UI、地图、环境贴图不缩小。

## 尺寸依据

不能只按手机的逻辑宽度选择贴图。正式项目逻辑宽度为 720；检查导出引擎的 `Stage.setScreenSize` 可知，微信非 DOM 画布还按设备像素比计算实际画布。应使用物理画布宽度除以逻辑宽度，再乘对象的最大显示尺寸。

本项目的选择规则为：

```text
候选纹理边长 = 向上取 16 的倍数（最大逻辑显示边长 × 1440 / 720 × 1.05）
实际发布边长 = 原规范化边长与候选边长中的较小值
```

1440 物理宽是本轮检查目标；1.05 是工程选择的采样余量，不是引擎要求。人物计入精英 1.25 倍体型，敌人计入最大 1.04 倍外观缩放，建筑检查全部 108 种布局，并计入升级动作 1.08 倍缩放。不是所有主体都能安全缩小，不能为了减少包体把全体资源统一缩成 128。

官方依据与本项目推导分开：

- Android Developers 建议在满足目标画质的前提下尽量减小纹理，并说明放大双线性纹理仍会模糊；本项目据此按实际像素占用计算，而不是只比较文件体积。见 [Textures](https://developer.android.com/games/optimize/textures)。
- Laya 提供双线性过滤；正式 `SpriteFrames` 已使用它，本轮沿用，不切回点采样。见 [FilterMode](https://layaair.com/3.x/api/3.4/enums/laya_RenderEngine_RenderEnum_FilterMode.FilterMode.html)。
- 画布与舞台缩放的含义见 [Stage](https://layaair.com/3.x/api/3.4/classes/laya_display_Stage.Stage.html)；本地导出的 3.4.2 引擎实现作为最终计算依据。

更高物理分辨率、大幅缩放查看或以后增大角色，必须重新计算。当前验证不代表任意设备、任意放大倍率下都不会出现采样损失。

## 分类发布尺寸

下表为规范化源画布边长，打图集时仍会裁掉透明空白并恢复偏移。

| 资源 | 原尺寸 | 当前尺寸 | 原因 |
| --- | --- | --- | --- |
| 成年男女、老人世界动画 | 256 | 240 | 最大精英画布约 225 物理像素，再留余量 |
| 孩子世界动画 | 256 | 208 | 最大精英孩子画布约 193 物理像素 |
| 婴儿动画 | 192 | 192 | 保留原尺寸 |
| 五类小怪主体 | 256 | 144 | 最大画布约 133 物理像素 |
| 五类首领主体 | 256 | 208 | 最大画布约 191 物理像素 |
| 怪物头饰、背饰 | 128 | 64 / 112 | 按挂点显示尺寸计算 |
| 三类塔第一档主体、伐木场主体 | 256 | 240 | 按实际布局边界与升级缩放计算 |
| 侧屋、门扇、武器及装饰部件 | 192 | 48～160，弓弩保留 192 | 每个部件使用自己的最大需求 |
| 民房、农田、城门及高档塔等大主体 | 256 | 256 | 当前需求接近或超过原纹理尺寸，继续缩小会损失清晰度 |
| 五类静态头像 | 原始尺寸 | 原始尺寸 | 详情与旅人面板会放大，不能跟世界动画一起缩 |

静态头像与原始站姿文件逐字节一致。其目的是保留已有大图清晰度，并非把原始头像升级成更高分辨率。

## 制作管线

1. `res/source/rendered2d/runtime-texture-sizes.mjs` 集中配置发布尺寸，避免在运行时代码散写像素值。
2. `prepare-production.mjs` 仍先从高清母版执行既有裁框、主体对齐和画布规范化。
3. 缩图前复制五张完整静态头像，ID 加 `portrait_` 前缀；运行时 `SpriteFrames.portraitId` 保持原有选人规则，只切换到独立头像 ID。
4. 对规范化后的完整画布使用 Lanczos 降采样，输出 8 位 RGBA；同步缩放脚底、裁框和原图映射信息。动画步幅仅乘一次比例，不能逐帧重新适配主体或原地重复修改共享 pivot。
5. 配方记录原规范化画布、缩放率与新输出哈希。规范化脚底位置以及 `stridePixels / canvasWidth` 保持不变。
6. 建筑和怪物的原生布局、96 单位敌人画布与挂点保持原样；同步编辑器引用贴图，原生 `.lh`、`.mc` 不重写。
7. 运行既有图集工具，沿用透明裁边、2 像素边缘外扩和双线性采样；九宫格不缩图。
8. 新旧白名单差集中的 `buildings_2.png`、`battle_1.png` 及对应派生副本、元数据移至 Downloads 归档。未知文件保护规则保留，不以递归清空目录代替白名单同步。

重建顺序仍为：高清母版 → 正式导入 → 同步资源配方 → 原生引用与图集同步 → 微信导出 → 包体与画面验证。实际命令入口见 [资源工程说明](../../res/README.md)。仅修改尺寸配置后也必须从母版重建，不对上次的小图反复缩放。

## 实测体积

统计对象为 `tryVersion/wxgame` 导出目录原始字节，不是微信上传后的压缩体积。1 MB 按 1,000,000 字节计算。

| 项目 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 完整导出目录 | 16,580,328 字节 | 14,897,507 字节 |
| 主包 | 3,914,036 字节 | 3,914,190 字节 |
| 运行图集 | 13 页 | 11 页 |
| 基础图集 | 2 页 | 2 页 |
| 建筑图集 | 3 页 | 2 页 |
| 人物图集 | 6 页 | 6 页 |
| 怪物图集 | 2 页 | 1 页 |

总计减少 1,682,821 字节，约 1.68 MB、10.15%。主包增加的 154 字节来自契约及头像 ID 代码，基础图片未变。当前建筑分包 3,067,814 字节，人物分包 6,678,000 字节，战斗分包 1,237,503 字节。

每页为 1024×1024 RGBA，全部加载时仅图集基础纹理的未压缩估算从 52 MiB 降至 44 MiB，减少 8 MiB。这不是 GPU 或进程总内存实测，也不包含帧缓冲等开销。

## 验证与证据

- TypeScript 编译通过，202 项回归检查全部通过。
- 48 组动画的帧数、顺序、帧率、方向保持一致；缩图后的脚底比例与步幅比例通过检查。
- 五张独立头像与缩图前原站姿文件逐字节相同。
- 380 项高清制作源、设计输入及原生预制体/时间轴哈希不变；导出的建筑与怪物布局 JSON 哈希不变。
- 包体检查无错误，发布图集减少两页，废弃页按白名单差集归档。
- 离线按目标物理显示大小制作人物、孩子、老人、小怪、首领、塔体和部件前后对照，检查面部、脚部、轮廓与透明边缘。前后不承诺像素完全相同。
- 微信开发者工具 iPhone 12/13 模拟器验证村庄、人物详情与守夜加载/战斗显示。模拟器截图是界面缩放后的画面，不能等同 1440 宽物理真机验收；本轮未新增手机真机实测。
- 在正式包的 Laya 渲染器内额外展示全部 5 类小怪、5 类首领，检查最大外观缩放以及另一帧的挂件、乘色和水平翻转；临时验证节点未写入代码或存档，检查后已移除。
- 26 项资源白名单与正式工程及导出包逐字节核对一致；Laya 发布的两段 `.mc` 按已有规则对应 `.mc.bin`。验收后清除本轮本地测试存档，重载正常回到开村界面。

全量回归曾发现旧攻击反馈用例把怪物出生点与第一座塔射程绑定。此前塔位下移后，该假设已不成立；用缩图前代码也能复现失败。本轮只修正测试夹具，让静止怪物位于每座已建塔附近的真实路径点，不改攻击规则或塔位。
