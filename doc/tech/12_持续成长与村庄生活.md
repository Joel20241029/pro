# 持续成长与村庄生活：设计、实现与验证

日期：2026-11-11。状态：用户已确认整套方案，代码、资源和数值模拟已实施，初次交付为配置 5。配置 6 的 UI 精修、表情和代码审查见 [13](13_UI精修与代码审查.md)，当前配置 7 的塔位和表情距离调整见 [14](14_塔位覆盖与表情距离.md)。下文成长数值保持有效；第 13 节保留初次交付的验证记录。

## 1. 已确认的目标

- 只面向微信小游戏，使用当前 Laya 3.4.2 工程和微信原生资源分包。
- 同一村庄持续成长，不强制轮回、转生或定期重建；守村失败仍按现有规则重新开村。
- 修正照料者面向孩子的方向，增加小体积背景音乐及 3 倍速。
- 民居、农田、伐木场、防御塔和敌人具备长期成长；同时处理仓库与城门的配套成长。
- 夜间驻塔者走进塔后隐藏，其余村民围火堆；照料者与孩子安排在一起。
- 选中驻塔人选并成功调任后直接关闭面板。
- 优化全部常用 UI 的信息层次、图标、文字和操作区；保留大字、描边、右上关闭、滚动列表、无按钮底部投影。
- 村民偶尔出现表情，临近退休、晚年与精英身份有相应表现；用户最新要求取消头顶台词。
- 出生与旅人帮助缓解男女失衡，不采用固定的一男一女交替序列。
- 同步代码、源资源、构建工具及文档。沿用不兼容旧配置的开发策略；交付时人工清除本地开发双槽存档，保留云端最高防守纪录。

## 3. 方案选择

采用“固定规模村庄 + 持续升级效率 + 持续成长敌人”。保留 20 人、4 个塔位、40 个同屏敌人、80 个计划单位的限制，延长游玩不增加对象池或地图大小。

用户已选定持续养同一村庄，因此不采用以定期重建换取成长的路线。自由扩张地图和无限增加人口会扩大移动、遮挡和资源成本，也不符合轻量单屏游戏的目标。

初版调平以 0 挑战档的正常经营为基准；已有 0～3 挑战档继续提供更强出兵预算。本轮不新增货币、广告、装备或自动保胜机制。

## 4. 持续成长数值

### 4.1 共同原则

- 建筑等级没有设计上的终点，使用公式计算，避免不断追加配置行。
- 数值采用线性成本及温和二次战力曲线，不使用指数翻倍。
- 农田最多 6 个岗位、伐木最多 4 个岗位，前三阶解锁岗位，后续提升单人效率。
- 人口仍受民居间数约束：初始 2 间，每间 4 人，最多 5 间 / 20 人。另设民居修缮等级，用于持续提升仓储。
- 升级会同时消耗木材和少量粮食，粮食除了口粮、生育还参与建设，避免农田后期失去意义。初次造房、造塔及改建费用先沿用现有木材规则。
- 升级预览、扣费、产出、战斗和存档验证读取同一组配置 / 纯计算函数，不各自复制公式。
- 下表系数已通过正常经营模拟验证；后续调参需同时重跑经济、人口与实际战斗。

### 4.2 建筑

`L` 是升级前等级，`n = L - 1`。表中产出为天赋、专长、季节和精英乘区之前的单人基础值。

| 对象 | 当前能力 | 升到下一级的当前成本（木 / 粮） | 说明 |
| --- | --- | --- | --- |
| 农田 | 每人 `8 + 2n` 粮；岗位 2、4、6，之后维持 6 | `40 + 25n` / `15 + 10n` | 第 4 级及以后持续提高效率 |
| 伐木场 | 每人 `6 + 2n` 木；岗位 2、3、4，之后维持 4 | `35 + 25n` / `15 + 10n` | 产出增长为建设提供持续收入 |
| 民居修缮 | 粮、木各可储存 `200 + 160n` | `30 + 25n` / `10 + 10n` | 不增加同屏人数，不自动发放物资 |
| 城门 | 最大耐久 `200 × P(L)`，向上取整 | `30 + 25n` / `10 + 10n` | 升级仅补足新增耐久；旧伤仍保留 |
| 防御塔 | 原塔基础伤害 `× P(L)` | `35 + 25n` / `10 + 10n` | 保留 3 种塔和现有兵种克制 |

`P(L) = 1 + 0.45n + 0.05n²`。前三阶正好是 1、1.5、2.1，与现有塔伤害系数衔接。攻击间隔、射程、减速上限不无限增加，避免无限射速或全图控制。

修门沿用木材支付：每次成本 `10 + 5n`，恢复最大耐久的 20%，再应用现有修门村规。修复量向上取整、以最大耐久为上限，满血不可购买。这样高等级城防不会出现固定修 40 点失去作用的问题。

民居的“增建房间”和“修缮民居”是两个明确操作：前者增加人口容量，后者提升仓储。房间建满时仍可修缮。若仓库不足以容纳某次升级费用，条目直接标出需要先修缮民居，不能只反复提示资源不足。

### 4.3 敌人与可持续性

- 保留第一年兵种解锁、季节权重、年度首领、随机词缀及有界出兵预算。
- 第 12 波后，设 `t = max(0, 波数 - 12) / 18`，基础生命与攻门伤害乘 `1 + 0.45t + 0.05t²`，再应用原词缀 / 村规。
- 第一年的基础属性保持不变；之后每波连续成长，不根据玩家建筑等级反向追平。
- 敌人速度、同时在场数、首领召唤次数不随年数无限增加。
- 改变配置只改变下一次生成的战前快照；守夜中的倍速、换人不重算或重开当晚敌人。
- 模拟必须包含连续生产、口粮、出生、退休、旅人、仓储和真实战斗。只有“给满资源 / 无限寿命”才能活下去的曲线不算通过。
- 必须存在一种可复现、无资源注入、无无限寿命、不依赖必出精英的经营策略，至少在 5 个普通固定种子中连续守住 300 夜，并包含实际生育、退休、调岗与真实战斗。只记录“全部早早失败”不能视为调平通过。
- 抽查第 1,000 / 10,000 / 1,000,000 波的数值有限性及对象上限。模拟策略、通过率、失败原因如实记录；这些检查不等同于证明所有决策都能永久存活。

## 5. 性别失衡与旅人

### 5.1 常态：带偏置的随机

统计在村的孩子和仍能劳作的成年人，老人不计入未来繁衍结构。设男性数 `M`、女性数 `F`：

- 新生儿为男性的概率：`50% + 25% × (F - M) / (F + M)`，限制在 25%～75%。
- 普通旅人为男性的概率：`50% + 35% × (F - M) / (F + M)`，限制在 15%～85%。
- 若两类人数均为 0，概率为 50%。人数相等也是 50%，连续同一性别仍可能发生。
- 只在真正生成新生儿 / 旅人时抽取；出生仍使用 family 流，旅人仍使用 world 流。开面板、预览条件、读档不重新抽取。
- 性别使用 `rng.next() / 2^32` 与上述概率比较，每次只消耗 1 个随机数；不再使用 `range(2)` 或其他小模数，以免 LCG 低位与整次出生消耗数量产生周期关联。精英、姓名、天赋等其他抽取维持原语义。

例：村里可计数男性 6 人、女性 2 人，新生女孩概率为 62.5%，普通女性旅人概率为 67.5%；并不是“生了男孩下一次就必须女孩”。

### 5.2 断档时：一次有针对性的来访

以下保护规则已经用户明确确认并实现：

1. 清晨结算后，如果某一种性别的劳作成人为 0，而另一种仍有劳作成人，下次生成的旅人采用缺少的成年性别。即使有该性别孩子，也先提供成年接班机会。
2. 此时可以把旅人提前到该清晨，但距离上次旅人来访至少 3 个已成功防守的夜晚；原本每 4 夜的正常来访时间点保留，但也受这 3 夜的最小间隔约束，距离紧急来访过近的正常来访直接略过。二者同日只出现一个旅人，不积累补发队列。
3. 若完全没有劳作成人且仍有空位，也可按相同冷却提前来访；性别依常态偏置随机，不一次塞入一对男女。
4. 记录的是上次“提供来访”的时刻，谢绝也计入冷却，避免每个清晨重复打扰。不因重开面板或重新启动刷新旅人。
5. 仍由玩家接纳 / 谢绝，不突破民居容量、不强制成家、不改变近亲限制。满员时只显示正常旅人事项及满员原因，不额外制造紧急来访。
6. 冷却状态属于当前村庄存档；新村初值明确为未发生来访，不给旧档补值。

该规则解决性别断档造成的长时间等待，不承诺所有亲缘、寿命和资源组合都必然可以生育。家庭面板继续显示真实阻塞条件。

## 6. 夜间生活与照料表现

- 以场景中的火堆为中心预设最多 20 个不重叠站点，沿现有导航绕开建筑；站点分配按稳定的人物 ID 顺序，不消费业务随机数。
- 照料者与孩子优先分配侧方相邻位置，其他成人、儿童、老人围坐。沿用原足底深度排序，火堆和建筑可以遮挡人物。
- 婴儿从出生起就在火堆旁的育儿位置播放 baby idle，白天照料者走到旁边，夜晚其他村民围过来。不新增抱起 / 运送 / 放下状态，不让婴儿自己走路或滑行；成长为儿童后再使用对应儿童 walk。
- 育儿位置按当前实际人口分配并稳定保留到孩子成长 / 离村，不能直接以永久人口编号取模，避免长期人口更替造成占位重叠。分配和导航测试需包括大量无人照料、尚未成长的孩子。
- 照料者若兼任守塔，夜间直接走入塔，婴儿仍留在育儿位置；现有照料结算规则不变。未驻塔的照料者优先站在自己的孩子旁。
- 照料时按孩子当前画面位置选择左右镜像；移动时继续使用已验证的方向 walk，不让劳动动作代替移动动作。
- 夜间临时换守塔人后，原守塔人走回火堆，新守塔人走入塔；不重启战斗、不清冷却、不清除用户主动暂停。
- 成功选择守塔人后自动关闭整个操作面板；校验失败时保留面板和错误信息。

## 7. 3 倍速与背景音乐

### 7.1 倍速

按 1× → 2× → 3× → 1× 循环，保存当前设置。逻辑保持固定 0.05 秒一步，单帧模拟预算覆盖最高 3 倍速下允许计入的 0.25 秒现实时间。暂停不累计时长，后台不追帧。

人物移动、帧动画和箭矢按同一战斗时间播放；Tip 和音乐使用现实时间。1/2/3 倍速在相同输入、相同模拟 tick 的结果必须一致。

### 7.2 音乐

- 制作一段原创、无歌词的轻柔循环：木质拨弦、简短五声音阶旋律和低音铺底，不占用人物或战斗系统。
- 目标 24～32 秒、单声道 MP3，成品优先控制在 120 KB 内；质量与体积以实际试听和编码结果为准。
- 保存可复现的音符谱、合成脚本、压缩参数和资源清单。发布仅带压缩成品，不带母版 WAV 或工具文件。
- 放入现有 `resources/village` 原生分包，通过已核实的微信 `createInnerAudioContext` 播放；主包不内嵌 base64、不新增外部下载或腾讯云服务。
- 首次有效玩家交互后开始；设置中可开关并保存。音量取低值，不随 3 倍速加快，遵循系统静音。
- 切后台、系统音频打断、销毁时暂停 / 释放。返回游戏或音频打断结束不会抢先播放，等玩家继续游戏 / 再次交互后恢复。
- 播放失败不阻止村庄逻辑；记录原始错误并给一次简短提示，不逐帧重试。用户再次主动打开音乐时才重新尝试。

音乐实际采用单个 `InnerAudioContext`：默认遵循系统静音，不更改全局音频选项。已移除会在开发者工具报“不支持”并阻断播放的冗余 `setInnerAudioOption` 前置调用；没有增加平台分支或静默重试。失败后主动关 / 开会销毁失败音轨并重建，旧对象错误回调按对象身份排除。

API 依据：[微信官方小游戏类型仓库示例](https://github.com/wechat-miniprogram/minigame-api-typings/blob/master/test/game.test.ts)、[InnerAudioContext 官方说明](https://developers.weixin.qq.com/minigame/dev/api/media/audio/InnerAudioContext.html)。实际路径必须在导出包内核验。

## 8. UI 改造

视觉方向保持森林像素村庄，主色使用深木棕 `#48311f`、浅纸色 `#fff1cf`、森林绿 `#557637`、铜金 `#d49a35`、湖蓝 `#356a86`。男名蓝、女名橘色延续；不足资源用红色，已满足条件用正常色。

不另加整屏高清背景或字体文件。优先复用现有建筑、职业、资源图标和紧凑九宫格；新增几何色块、分隔、进度条用 Laya Graphics。若需要新增位图，必须同时保存原图及配方，不能只改导出的图集。
