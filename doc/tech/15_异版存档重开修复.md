# 代代守村：异版存档重开修复

日期：2026-11-11。该修复本身沿用配置 7；同轮自动驻塔将当前配置提升为 8，见 [16](16_防塔自动驻守.md)。本篇只记录启动读档的操作死路与确认重开的双槽提交，不改变存档结构、玩法数值或图片资源。

## 1. 问题与证据

旧流程在任意一个槽的 `schemaVersion` 或 `configVersion` 不匹配时返回 `blocked`，且 `canReset=false`。启动面板只有“重新读取”；按钮经 `GameSession.retry()` 再次调用 `SaveStore.inspect()`，得到同一个阻断结果。按钮回调实际执行，但无法进入游戏，表现为卡死。

另一个关联问题是旧 `allowReset()` 仅重置内存提交序号，新村第一次保存只覆盖一个槽。如果另一槽仍是异版，下一次启动又会阻断。两种问题均在修改前使用原始编译代码复现。

## 2. 经审核的修复方案

- 版本不匹配返回独立 `incompatible` 状态，显示“存档版本已变化”，解释旧进度不能用于当前版本。
- 提供“确认放弃旧进度，重新开村”，移除这个状态下无效的“重新读取”。玩家确认前只读存档，确认后才替换旧进度。
- 复用 `GameSession.newVillage()`、`SaveStore.prepare()/commit()` 和已有保存失败重试面板。显式重开直接创建新村，不继承可能残留在内存中的传承、家谱和收藏。
- 异版与确认放弃的损坏档使用双槽提交；正常同版进度、存储读取异常和有效存档冲突不能通过这个入口重置。
- 保留正常双槽轮换、校验、损坏恢复和并发保护，不增加跨版本迁移或启动自动清档。

方案经独立只读审核后实施。项目没有 `PopupCheckPoint` 定义；本次为 Laya 启动读档界面及其存储流程修复。

## 3. 双槽提交与中断边界

`pending.reset` 只保存在内存中，不写进存档封套。确认重开后生成一个固定候选，新提交序号为 1。

1. 写入前读取两个槽；每个槽必须仍等于确认时的原始内容，或等于同一待提交候选。任何其他变化都停止覆盖。
2. 当前/异版混合时，先写非异版槽，再写异版槽；两个槽均异版时从 A 槽开始。这样在第一槽完成后退出，至少仍保留一个异版槽阻断，不会重新读回已经确认放弃的高序号旧村。
3. 两个槽都写成同一候选，读回核对两个槽完全一致之后，才进入新村。
4. 同一会话内写前、写后或读回失败均保留候选，显示已有“核对 / 重试保存”，重试不重新生成村庄或随机种子。
5. 异版双槽尚未写完时强退，下一次进入仍需要明确确认重开；不宣称跨进程恢复内存中的待提交事务。两个槽已写完但读回失败时，下一次启动可以读取已保存的新村。

仅替换 `daidai_village.save.a` 和 `daidai_village.save.b`，不清空其他微信缓存或好友榜云成绩。无法解析的旧本地传承不迁移，新村本地最高波数从 0 开始；这不等于删除微信云端最高纪录。
